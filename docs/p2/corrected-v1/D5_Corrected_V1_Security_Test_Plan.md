## 1. Test method and evidence

Use the dedicated Dev project only. Create explicitly labeled test tenants/users inside isolated test transactions or a controlled test fixture process; never seed fake production organizations or business statistics. Concurrency tests require independent real database/API sessions and controlled cleanup because a single rolled-back transaction cannot prove inter-session behavior.

For each executed test record:

- test ID, exact schema/migration version and timestamp;
- actor/session type and fixture IDs;
- operation and relevant committed/rollback state;
- expected versus actual result, including error code where appropriate;
- counter/audit/branch/membership reconciliation queries;
- pass/fail/blocked status and any deviation.

Do not convert a permission error into proof of RLS by assumption: distinguish ACL denial, RLS empty results, policy rejection and RPC authorization errors. Test direct PostgREST/RPC calls as well as UI behavior.

## 2. Fixture matrix

Proposed isolated fixtures:

- Tenants A and B, both active; Tenant C suspended and Tenant D archived for negative tests.
- Tenant A branches A1 and A2; Tenant B branch B1. An inactive branch A3 for lifecycle tests.
- Verified users: Owner O1, second Owner O2, Organization Admin OA, Branch Manager BM(A1), Staff S(A1), Read Only RO(A1), outsider X with no A membership, and verified user I for invitations.
- An unverified Auth user UV and verified users with emails matching/not matching invitation recipients.
- Custom roles CRA in Tenant A and CRB in Tenant B, created only by controlled fixtures; custom-role management feature remains disabled.
- Independent sessions for O1/O2, inviter/invitee and concurrent revocation/acceptance.

All fixture identity/role rows must obey the actual P1 global-system-role semantics. No test may use rank or display name alone to fabricate Owner authority.

## 13. Phase-specific release acceptance criteria

### P1 prerequisites

P1 execution and acceptance require separate exact-V3 approval, fresh Dev preflight, live schema/ACL/RLS inspection and the P1 parent/prerequisite tests with actual evidence. No P2/P3 guarantee is inferred from P1.

### P2 security acceptance

P2 requires every P2 parent test and all mandatory earlier subsets of composite tests, including real JWT/PostgREST policy evidence, exact ACL/owner/helper inventories, branch/history validation, private audit/catalog guards, Owner primitive two-session races, counter tampering, rollback and measured P2 policy-plan/primitive-stress evidence against approved budgets. P3/P4/P9 parents remain blocked, not waived or passed.

### P3 and deployment

P3 requires accepted P2, separate implementation approval, controlled initialized profiles, authoritative country/currency validation, exact settings/retry/offboarding contracts where used, durable direct-RPC/wrapper controls and approved numeric limits/budgets. Browser transport waits for the relevant UI phase. Public self-service onboarding waits for P4/P5.

### P4 and P9

P4 owns profile initialization/self updates and Auth lifecycle evidence. P9 owns verified-UUID Platform Admin bootstrap/lifecycle and platform operations. Neither is a P2/P3 acceptance claim.

A release is rejected for cross-tenant/unassigned-branch exposure, excess direct/service privilege, Owner drift/zero-Owner commit, platform escalation, token/hash disclosure, acceptance after invalid state, mutable audit/catalogs, recursive/mutable helpers, durable-control bypass, or any unexecuted/failed/flaky test reported as passed.
